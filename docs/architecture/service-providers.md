# Service Providers

Service providers are the main extension point for registering application services and bootstrapping application-level behavior.

## Provider lifecycle

Every provider inherits from `PixelFix\Framework\Providers\ServiceProvider` and can implement:

```php
public function register(): void
public function boot(): void
```

`register()` should define bindings. `boot()` should configure behavior that can safely run after the application's services have been registered.

## Example: authorization provider

The example application defines an application provider for a gate:

```php
class AuthServiceProvider extends ServiceProvider
{
    public function register(): void
    {
        // Register services here.
    }

    public function boot(): void
    {
        Gate::define(
            'access-admin',
            function ($user): bool {
                return $user->role === 'admin';
            }
        );
    }
}
```

A separate provider registers model policies with the framework's `PolicyRegistry`.

## Event infrastructure and application registration

The framework's `PixelFix\Framework\Providers\EventServiceProvider` registers the event dispatcher and its supporting services. It is framework infrastructure; it does not declare application event-to-listener mappings.

The application-level `App\Providers\EventServiceProvider` is generated by `make:provider EventServiceProvider`. Like the specialized policy and middleware application providers, it extends `PixelFix\Framework\Providers\ServiceProvider`. Its `$listen` and `$subscribe` definitions are registered during `boot()` through `EventDispatcherInterface`. The `make:listener` command updates `$listen` when a listener is generated with an event relationship.

Do not extend or register a separate event-specific framework provider base for application mappings. The framework event provider is responsible for dispatcher bindings; the generated application provider is responsible for application listeners and subscribers.

## Deferred providers

The base provider exposes `isDeferred()`, `provides()`, and `when()` hooks. These are part of the provider infrastructure. Use them only when the application's registration requirements justify deferred loading or conditional provider behavior.

## Provider responsibilities

Good provider responsibilities include:

- registering interface implementations;
- configuring authorization gates and policies;
- configuring framework integrations;
- attaching application-level listeners or behavior supported by the current framework.

Avoid placing ordinary request handling or feature logic in providers. Put feature behavior in controllers, services, models, policies, or other appropriate application classes.


## When should code run in a provider?

Use a provider to register a binding, configure a framework facility, or perform one-time application boot setup. Do not run request-specific queries or send an email merely because the provider is booting; the provider lifecycle may run before many different requests and console commands.

A common example is registering an interface-to-implementation binding during registration, then allowing a controller to request the interface in its constructor. Registration tells the container how to build the service; resolving the controller later causes the service to be constructed when needed.

## How to diagnose a provider that does not run

Check that the provider is listed in the active application configuration and that the configuration file is actually loaded by bootstrap. Then check the appropriate lifecycle method—registration and boot work have different purposes. If the provider itself throws, read the first exception because later container errors may be consequences of that failure.
